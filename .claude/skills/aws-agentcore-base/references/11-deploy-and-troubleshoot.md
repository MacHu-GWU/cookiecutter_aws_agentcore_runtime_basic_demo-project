# Deploy and Troubleshoot

---

## 1. The deploy chain

Three steps, in this order, each its own task; `ac-chain-up-<env>` runs all three:

| # | Step task | Does | Why here |
| :--- | :--- | :--- | :--- |
| 1 | `config-deploy-<env>` | the config to SSM, only if it changed (`06`) | the runtimes read it at startup |
| 2 | `cdk-up-<env>-agentcore-deps-stack` | what the runtimes use but is not AgentCore (`07`) | `agentcore.json` refers to its policy |
| 3 | `ac-deploy-<env>` | the AgentCore runtimes (section 2) | needs 1 and 2 |

```bash
mise run ac-chain-up-<env>     # the whole chain
mise run ac-invoke-dev-agent   # dev only: ask the deployed SiteAgent the demo question
```

A chain prints the whole chain first; every step prints `>>> <task>: <what it does>` before its own output, so the log of a chain reads as the list of its steps. The chain stops at the first step that fails. Run a single step on its own when only that part changed: a config change needs only step 1 (a new runtime session reads it), a policy change only step 2, a code change only step 3.

The CDK bootstrap stack (`CDKToolkit`) must exist in the account and region.

**Every step and chain changes AWS: the user runs it, or says yes to it, one environment per yes.** Free to run: `ac-gen`, `ac-build` (synth only), `ac-check-wheels.py`, `ac-check-layout`, `cdk-synth-*`, `cdk-plan-*`, `mise run -n <task>` (dry run: prints what a task would run).

## 2. What `ac-deploy-<env>` does

Generated by `mise run gen-env-tasks` (`cdk/mise_tasks.py`), with `ENV_NAME=<env>`; each command stops the task when it fails:

1. The banner, then the AgentCore stack's console URL.
2. `ac-check-deps.py`: the `agentcore_deps` policy and the config parameter exist, else print the task to run for each.
3. `ac-gen.py`: `agentcore.json`, `aws-targets.json`, `app/` for `<env>`.
4. `ac-check-wheels.py`: every runtime's dependencies install as the CLI installs them (`04`).
5. `AWS_PROFILE=<profile of env> agentcore deploy --target <env>`: the CLI checks the profile's account matches the target, synthesizes (`agentcore/cdk`), packages the CodeZips, deploys the stack.

It does not deploy the config itself: that is step 1 of the chain.

---

## 3. Invoke and logs

- `agentcore invoke --target <env> --runtime <Runtime> --payload '<json>'` with `AWS_PROFILE` set. Add `--session-id <id>` to reuse a session (`02`).
- Each runtime logs to `/aws/bedrock-agentcore/runtimes/<runtime ID>-DEFAULT` (`05`), one log stream per session. `agentcore logs runtime` streams or searches them too.
- A healthy start prints `Loaded the config of '<env>' on runtime 'agentcore'` (and `Connected to the database ...` for the MCP runtime) (`06`).

## 4. Failures met so far

| Symptom | Cause | Fix |
| :--- | :--- | :--- |
| `Received error (500) from runtime` on invoke | an exception in the runtime | read the runtime's log (section 3); the traceback is there |
| `AccessDeniedException` for a Bedrock model, `agreementAvailability` `NOT_AVAILABLE` | the model's agreement is not available in the account (it happened for Claude Haiku 5.5), whatever the console's model access page shows | use a model the account can call; check with `bedrock get-foundation-model-availability`. Never accept a Marketplace agreement for the user |
| `ValidationException: Error 002: Access to Bedrock models is not allowed for this account` | the profile signs in to a different account than the config's | point `AWS_PROFILE_FOR_<ENV>` in `.env` at the config's account; run through mise (a shell without mise does not load `.env`) |
| `uv install failed for all platform candidates` at synth | a dependency version without a Linux aarch64 wheel | `ac-check-wheels.py` names it; exclude the version (`04`) |
| `The policy ... does not exist` from `ac-deploy` | `agentcore_deps` not deployed | `mise run cdk-up-<env>-agentcore-deps-stack` |
| `config SSM parameter ... does not exist` at startup | the config was never deployed (or was deleted) | `mise run config-deploy-<env>` |
| `Deployment target '<env>' expects AWS account ...` | the profile's account is not the target's | as for Error 002 |
| `CDK dependencies are missing` | `agentcore/cdk/node_modules` absent (fresh clone) | `npm install` in `agentcore/cdk` |
| a deploy does not change a running session | a microVM keeps the code it started with | a new session gets the new code (`02`) |
| `Unknown runtime "<Name>" in project` at synth | a `runtime('<Name>')` in `cdk-stack.ts` that `agentcore.json` does not declare | run `ac-gen`; keep `bind()` inside `if (this.application.runtimes.size > 0)` |

## 5. The teardown chain

The deploy chain in reverse; `ac-chain-down-<env>` runs all three, after asking for confirmation (`mise run --yes` skips the prompt):

| # | Step task | Does |
| :--- | :--- | :--- |
| 1 | `ac-down-<env>` | the AgentCore stack: every runtime of `<env>` |
| 2 | `cdk-down-<env>-agentcore-deps-stack` | the `agentcore_deps` stack, once no role uses its policy |
| 3 | `config-delete-<env>` | the config parameter |

```bash
mise run ac-chain-down-<env>
```

`ac-down-<env>` is the CLI's own teardown: `agentcore deploy --yes` of a project that declares nothing destroys the target's stack and removes the target from `agentcore/.cli/deployed-state.json`. Here `agentcore.json` is generated, so instead of `agentcore remove all` the task writes an empty one (`.mise/tasks/ac-gen-teardown.py`), deploys it, then runs `ac-gen` to put the real project back. If the deploy fails, the empty `agentcore.json` stays until the next `ac-*` task regenerates it. `cdk-stack.ts` skips `bind()` when there is no runtime, so the empty project still synthesizes.

Commit the changed `deployed-state.json` afterwards.

---

## 6. `deployed-state.json` stays in git

`agentcore/.cli/deployed-state.json` records each deployed target's stack (and credential provider ARNs, none here). The `.gitignore` of a fresh `agentcore create` commits it on purpose, so everyone who deploys shares it; keep it committed, and commit it after every deploy or teardown that changes it. With several deployers, give each environment one deployer (in the end, CI), so two people never write it for the same target at once.
