# Deploy and Troubleshoot

---

## 1. First deploy of an environment

```bash
mise run cdk-up-<env>-agentcore-deps-stack   # what the runtimes use but is not AgentCore (07)
mise run ac-deploy-<env>                     # config, checks, ac-gen, agentcore deploy
mise run ac-invoke-dev-agent                  # dev only: ask the deployed SiteAgent the demo question
```

The CDK bootstrap stack (`CDKToolkit`) must exist in the account and region. Later deploys need only `ac-deploy-<env>`, plus `cdk-up-<env>-agentcore-deps-stack` when that stack changed.

**Every one of these changes AWS: the user runs it, or says yes to it, one environment per yes.** Free to run: `ac-gen`, `ac-build` (synth only), `ac-check-wheels.py`, `cdk-synth-*`, `cdk-plan-*`.

---

## 2. What `ac-deploy-<env>` does

Generated by `mise run gen-env-tasks` (`cdk/mise_tasks.py`), with `ENV_NAME=<env>`; each step stops the task when it fails:

1. `inst`, then `config-deploy-<env>`: the config to SSM, only if it changed (`06`).
2. Print the AgentCore stack's console URL.
3. `ac-check-deps.py`: the `agentcore_deps` policy exists, else print which task to run.
4. `ac-gen.py`: `agentcore.json`, `aws-targets.json`, `app/` for `<env>`.
5. `ac-check-wheels.py`: every runtime's dependencies install as the CLI installs them (`04`).
6. `AWS_PROFILE=<profile of env> agentcore deploy --target <env>`: the CLI checks the profile's account matches the target, synthesizes (`agentcore/cdk`), packages the CodeZips, deploys the stack.

---

## 3. Invoke and logs

- `agentcore invoke --target <env> --runtime <Runtime> --payload '<json>'` with `AWS_PROFILE` set. Add `--session-id <id>` to reuse a session (`02`).
- Each runtime logs to `/aws/bedrock-agentcore/runtimes/<runtime ID>-DEFAULT` (`05`), one log stream per session. `agentcore logs runtime` streams or searches them too.
- A healthy start prints `Loaded the config of '<env>' on runtime 'agentcore'` (and `Connected to the database ...` for the MCP runtime) (`06`).

## 4. Failures met so far

| Symptom | Cause | Fix |
| :--- | :--- | :--- |
| `Received error (500) from runtime` on invoke | an exception in the runtime | read the runtime's log (section 3); the traceback is there |
| `AccessDeniedException` for a Bedrock model, `agreementAvailability` `NOT_AVAILABLE` | the model's agreement is not available in the account (it happened for Claude Haiku 5.5), whatever the console's model access page shows | use a model the account can call; check with `bedrock get-foundation-model-availability`. Never accept a Marketplace agreement for the user |
| `ValidationException: Error 002: Access to Bedrock models is not allowed for this account` | the profile signs in to a different account than the config's | point `AWS_PROFILE_FOR_<ENV>` in `.env` at the config's account; run through mise (a shell without mise does not load `.env`) |
| `uv install failed for all platform candidates` at synth | a dependency version without a Linux aarch64 wheel | `ac-check-wheels.py` names it; exclude the version (`04`) |
| `The policy ... does not exist` from `ac-deploy` | `agentcore_deps` not deployed | `mise run cdk-up-<env>-agentcore-deps-stack` |
| `config SSM parameter ... does not exist` at startup | the config was never deployed (or was deleted) | `mise run config-deploy-<env>` |
| `Deployment target '<env>' expects AWS account ...` | the profile's account is not the target's | as for Error 002 |
| `CDK dependencies are missing` | `agentcore/cdk/node_modules` absent (fresh clone) | `npm install` in `agentcore/cdk` |
| a deploy does not change a running session | a microVM keeps the code it started with | a new session gets the new code (`02`) |

## 5. Not automated yet

- Tearing an environment down. The CLI's way is `agentcore remove all` then `agentcore deploy`, which edits `agentcore.json` (generated here); deleting the stack `AgentCore-<Project>-<env>` is the alternative. Then `cdk-down-<env>-agentcore-deps-stack` and `config-delete-<env>`. Ask the user before each.
- `agentcore/.cli/deployed-state.json` is committed; fine with one deployer, a source of conflicts once several people or CI deploy.
